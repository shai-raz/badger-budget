# demo

Generates the demo account's transaction data and balance tiles. Shared by two callers: `prisma/seed-demo.ts` (initial seed, which runs only with `SEED_DEMO=true`) and `DemoService.topUpIfStale` (keeps it current on login). Has no controller — it's invoked from `AuthService`, not the HTTP layer.

- 5 accounts total: `DEMO_BANK_ACCOUNT_NAME`/`DEMO_CARD_ACCOUNT_NAME` (real transaction history, see below) plus 3 balance-only accounts from `demo-balances.ts` — a savings account (`account_balance`), a Cal-style card (`next_charge`), and a no-credit-limit card (`utilized_credit`, no `cardFrame`). `DEMO_CARD_ACCOUNT_NAME` doubles as the 5th balance variant, Isracard-style `utilized_credit` **with** a `cardFrame`.
- `demo-balances.ts` writes the same denormalized `accounts.balance`/`balanceKind`/`balanceDate`/`balanceUpdatedAt`/`cardFrame` columns `AccountBalanceService.recordBalances` writes for a real scraped balance (see `accounts/AGENTS.md`) — `refreshDemoBalances` computes them (bank/savings from the bank account's real ledger; the 3 cards scaled off the reused card's real current-cycle spend, or a fallback range when that's 0) and `ensureDemoBalanceAccounts` creates the 3 new accounts the first time they're missing. Both run from `seed-demo.ts` (initial seed) and from `DemoService.refreshBalances` on **every** `topUpIfStale` call, unconditionally — unlike the transaction top-up below, this isn't gated behind the `demoDataThrough` watermark, since the balances must look current on every login even on a day that adds no new transactions. `refreshBalances` has its own try/catch so a balance-refresh failure can't roll back (or be rolled back by) the separate transaction top-up.
- `ensureDemoBalanceAccounts`'s idempotency is a find-then-create check (`accounts` has no unique `(userId, name)`), so `DemoService.refreshBalances` serializes per user by writing the user row (`updatedAt`) at the start of its transaction, before any read — the row lock makes an overlapping login wait and then see the committed accounts. Without it, concurrent logins on a user lacking those 3 rows create permanent duplicates.
- `users.demo_data_through` is a watermark: the last calendar day demo transaction data has been generated through. `topUpIfStale` only advances it via a conditional `updateMany` (`where: { demoDataThrough: stored }`) inside the same `$transaction` as the generation + trim — a concurrency guard (same pattern as `AccountsService.upgradeUnknownAccountTypes`). A second call racing in for the same user matches nothing once the first has advanced the watermark, so it gets `count === 0` and backs off instead of double-generating. If generation or the trim throws, the whole transaction rolls back, including the watermark bump.
- A `NULL` watermark (pre-existing demo user, or the column predates them) is bootstrapped from the latest salary transaction's month-end — the seed generated data through the end of that month. This lookup ignores `deletedAt` on purpose: a soft-deleted salary (the demo login is public, so anyone can delete one) still marks where the seed left off, and honoring the filter would regress the watermark and regenerate a month that already has data. No salary at all means no demo data yet, so top-up generates the whole rolling window.
- `demo-data.generator.ts` writes one month at a time, chronologically, one `createMany` per month: a salary on a deterministic day in 1-5 (`demoSalaryDay`, stable per month so disjoint top-up windows never double- or zero-salary a month), a card payoff on the 15th sized from a DB `aggregate` of that account's stored previous-month card expenses (not recomputed in memory), weighted card expenses and 1-3 manual "Cash – …" bank expenses a month (both scaled down for a partial-month range). Salary/payoff/card rows get a synthetic `demo-<uuid>` `externalId` (`demoExternalId`, so they read as synced and the edit lock applies); cash rows have none, so they stay editable. Each month also gets one synced card ATM withdrawal (`buildDemoAtmWithdrawal`: `DEMO_ATM_DESCRIPTION`, uncategorized, `additionalDescription = CASH_WITHDRAWAL_LABEL` so the web cash-withdrawal hint fires) on a deterministic day 6-25 (`demoAtmDay`, never a salary day or the 15th) with an amount from `DEMO_ATM_AMOUNTS` indexed by month — no faker calls, so the seeded sequence is unchanged. `CASH_WITHDRAWAL_LABEL` is inlined in `demo-data.constants.ts` (seed-demo's ts-node can't resolve `@badger/shared-data`); keep it in sync. No cash account is pre-created for the demo. `postedDate` is clamped to the requested `to` date so a top-up never writes a posted date in the future.
- All dates are UTC-midnight date-only `Date`s produced by `toDateOnly` (`@db.Date` columns) — never pass a timestamp with a time component in.
- `topUpIfStale` also trims anything older than the rolling `DEMO_WINDOW_MONTHS` window with a **hard** `deleteMany`, the deliberate exception to the app's soft-delete convention: this data is regenerable and a public demo login endpoint would otherwise accumulate soft-deleted rows forever, including ones the user themselves deleted.
- One-time reseed: `topUpIfStale` first probes for any `demo-` externalId row (ignoring `deletedAt`). A user with rows but none of them (seeded before synthetic ids existed) gets a hard `deleteMany` of all their transactions and a full-window regenerate, in one `$transaction` with the same watermark CAS plus an in-tx re-check of the probe, so a racing login deletes nothing. After that the probe passes and the normal top-up runs.
- One-time ATM backfill: `topUpIfStale` calls `backfillAtmWithdrawals` on every path (before `refreshBalances`, own try/catch) so demo users whose window predates the ATM row get this and last month's. It locks the user row, then probes for any `demo-` row with the cash-withdrawal label **ignoring `deletedAt`** — a visitor-deleted one must not come back — and inserts only dates within `[windowStart, today]`.
- `prisma/seed-demo.ts` imports this folder via **relative paths only**: the seed (ts-node in dev, `tsc` in the image) has no path-alias support, so `@/...` aliases won't resolve there. The app has no `@/` imports either, so use relative paths throughout.
- `faker.seed(...)` is called only in `seed-demo.ts`, once, for reproducible initial data. Top-up generation is intentionally unseeded (real, if fake, variety over time).
- Triggered only from `AuthService.login` for `DEMO_EMAIL` on a successful password login; errors are logged, never thrown — a top-up failure must not fail the login.
- Non-goals: no cron/scheduled job (top-up is login-driven only), and the refresh-token path does not top up (only a fresh password login does).
- Demo icons (category `icon`s, salary, balance-account `icon`s, and the literals in `prisma/seed-demo.ts`) must be `AVATAR_ICON_NAMES` values from `@badger/shared-data`; `demo-icons.spec.ts` enforces it. Keep literal strings here, since seed-demo can't resolve the package.
