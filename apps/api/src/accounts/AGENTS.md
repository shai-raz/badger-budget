# accounts

Financial accounts (bank, cash, credit card, etc.) a user's transactions and budgets attach to.

- Plain CRUD, soft-deleted, scoped by `userId`.
- `AuthService.register`/Google sign-up create a default "Cash" account for every new user — see `auth/AGENTS.md`. That default, the cash-withdrawal suggestion and the cash descriptions stay cash-only; savings is never auto-created.
- Accounts carry a `currencyId`; transactions can be in a different currency than their account (which is where `transactions/fx-conversion.service.ts` comes in), except ledger accounts (`cash` and `savings`, `isLedgerAccountType` in `@badger/shared-data`): they must always have a currency and their transactions must use it (enforced in `AccountsService` and `TransactionsService.assertAccountCurrency`).
- `account-balance.service.ts` records balances captured during bank sync: it appends to `account_balance_snapshots` and refreshes the `balance` / `balanceKind` / `balanceDate` / `balanceUpdatedAt` / `cardFrame` / `cardIssuer` columns here. `balanceKind` is not decoration — it says whether the number is money in the account, a card's next charge, or consumed credit (see `bank-sync/AGENTS.md`), so don't sum balances without checking it. `cardFrame` (a card's credit limit) must never be summed across accounts either: Cal reports one group-level frame on every card in the issuing agreement. All these columns are a _latest observation_ and are written unconditionally, nulls included — the snapshot table keeps the history. The service also creates accounts for balance-only scraped accounts.
- `AccountsService` queries always `include: { currency: true }` and pass the row through `account-response.mapper.ts`'s `toAccountResponse`, which converts the `balance`/`cardFrame` `Decimal` columns to numbers — never return a raw Prisma `Account` row from a controller-facing method (`Decimal.toJSON()` serializes to a string, not a number).
- `upgradeUnknownAccountTypes(userId, accountNumbers, type)` types accounts that bank sync auto-created, from the provider's `ACCOUNT_TYPE_BY_COMPANY` entry. The `type: "unknown"` filter lives in the `where` — it is a safety mechanism, not an optimization: it keeps the match atomic instead of a racy read-modify-write, and is what makes the sweep idempotent. Don't lift it out. It is _not_ a guarantee that a user-set type survives, though — the web form and `UpdateAccountDto` both accept `"unknown"`, so an account deliberately reset to it gets re-typed on the next sync.
- `default-account-currency.ts` holds the currency fallback used when auto-creating an account; shared with `transactions/transaction-import.service.ts` — don't duplicate it.
- **Ledger balances are computed, not stored.** `ledger-balance.ts`'s `computeLedgerStats` (two `groupBy`s) derives, for ledger accounts (cash and savings), `balance` = income + transfers in − expenses − transfers out over the account's own non-deleted transactions (hidden included; null transfer direction = out), in cents. `AccountsService.withLedgerStats` overlays `balance`, `balanceKind` (`cash_on_hand` for cash; savings reports `account_balance`, so it sums with bank balances), `lastTransactionDate`, `hasLinkedTransfers` (any row that is a mirror or has a counterpart) and `hasTransactions` (any non-deleted row) in `findAll`/`findOne`/`create`/`update`. A ledger account with no rows keeps null balance/kind. `cash_on_hand` is never summed with bank balances. Nested `account` objects inside transaction responses come from `toAccountResponse` alone, so they carry no computed balance (`false`/`null` defaults).
- **One currency per ledger account.** A ledger account with any non-deleted transaction can't change currency (400; `hasTransactions`). An account can't become a ledger type (`cash` or `savings`) while any non-deleted transaction on it is in a currency other than the resulting one (400; checked against the currency in the same request). Linked accounts (`hasLinkedTransfers`) are stricter: they also can't be deleted, and can't change type at all, including cash<->savings (400).
- `POST /accounts/:id/balance` (`updateLedgerBalance`, body `{ amount, date }`) sets the balance the user actually has, for cash and savings. The **server is authoritative for the difference**: inside one `$transaction` it locks the account row (touching `updatedAt`), recomputes the balance, and records `amount − computed` (in cents). Cash: an uncategorized expense "Untracked cash spending" (shortfall) or a transfer-in "Cash adjustment" (surplus). Savings: always an uncategorized transfer, in when the balance rises and out when it falls, described "Savings adjustment". No difference → no row (`adjustment: null`). Descriptions live in `@badger/shared-data`. The client sends `date` (its local YYYY-MM-DD) because `transactionDate` is `@db.Date` and the server can't know the user's local day. The row is uncategorized so it needs no budget FX snapshot; recategorizing later goes through `TransactionsService.update`.
