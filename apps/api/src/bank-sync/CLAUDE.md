# bank-sync

Automates transaction import from Israeli banks via `israeli-bank-scrapers` + `puppeteer-extra` (stealth plugin). See the root `apps/api/ARCHITECTURE.md` for the high-level picture; this file is implementation-level notes.

- Scraper credentials are never stored in plaintext — they're encrypted with a user-chosen sync **PIN** (separate from their login password) via `crypto/CLAUDE.md`. If a user hasn't set a PIN yet (`getSyncPinStatus`), connections can't be created.
- `ScraperConnection` rows hold the encrypted blob; `UserSyncSecret` holds the PIN verifier. Losing/rotating the PIN (`setPinOrChange`) runs in a transaction, re-encrypts the verifier, and deletes all the user's `SyncPasskey` rows when a secret already existed, but does **not** re-encrypt existing connection credentials — check how PIN rotation interacts with already-stored credentials before touching that flow.
- `SyncPasskey` rows store only a browser-side PRF-wrapped PIN plus a per-credential `prfSalt`; there is no server-side WebAuthn. Registration is gated by `verifyPin`, capped at `MAX_PASSKEYS` (`@badger/shared-data`) per user, and a duplicate `credentialId` returns 409.
- Scraping runs either against a remote Browserless instance (`BROWSERLESS_URL`) or launches local Chromium. The production Docker image ships Debian's `chromium` and sets `PUPPETEER_EXECUTABLE_PATH` plus container-safe `PUPPETEER_ARGS`; `BROWSERLESS_URL` still overrides that. The stealth plugin applies on both paths: without `BROWSERLESS_URL`, `scrapeConnection` launches headless Chromium through `puppeteer-extra` (`launchLocalBrowser`) and hands it to IBS as `browser`, since IBS alone would launch plain puppeteer; it closes that browser in a `finally`. `mapWithConcurrency` (`concurrency.util.ts`) caps simultaneous scraper sessions via `BANK_SYNC_CONCURRENCY`. The same util is reused by `reports` for FX fetches.
- On scrape failure, `debug-artifact.service.ts` uploads screenshots/MHTML to Cloudflare R2 (`R2_*` env vars) when configured. Local copies are opt-in via `STORE_SCRAPER_DEBUG_LOCALLY=true`, written to `resolveDebugArtifactsDir()` (`config/data-dir.ts`); with neither, nothing is stored (no automatic local fallback). Artifacts are bank-page screenshots/HTML, so treat them as sensitive.
- Scraped rows are handed to `transactions/transaction-import.service.ts`, not written directly — that's the shared dedup/category-resolution path also used by `google-sheets`.
- `scrapeConnection` returns `{ candidates, balances }`. Balances are pulled off the scraped accounts by `scraped-balance.util.ts` (not summed from transactions — the identifier-less rows we skip would under-count cards) and persisted by `AccountBalanceService` after the import succeeds, in its own try/catch so a balance failure never fails an otherwise-good scraper job.
- **`balance` does not mean the same thing per provider.** Banks report money in the account; `visaCal` alone reports the next debit total (`next_charge`); `max`, `isracard` and `amex` all report _consumed credit_ (`utilized_credit`) — that's the majority kind, not the exception. `@badger/shared-data`'s `BALANCE_KIND_BY_COMPANY` maps each provider to its `BalanceKind`, which is stored on every snapshot — never sum across kinds. (`BalanceKind` also has `cash_on_hand`, a cash account's computed balance — never scraped, so it is absent from this map; see `accounts/CLAUDE.md`.) No provider maps to `null` today; the `null` arm stays because `getBalanceKind` takes a bare `string` and a future provider may be uninterpretable, and a `null` kind is skipped rather than guessed. union and yahav never return a balance in practice. The map is a total `Record<BankCompanyId, …>`, so a new provider won't compile until its semantics are declared.
- `cardFrame` (the card's credit limit) and `cardIssuer` (IBS's `cardType`, Cal-only) ride along on every snapshot and on the denormalized `accounts` columns. Card providers only. **Never sum `cardFrame` across accounts** — Cal's frame is _group-level_, the limit of the whole issuing agreement repeated on every card under it. A frame of `0` means a cancelled card and is stored as NULL. Both columns are written unconditionally, nulls included: they're a latest observation. That only covers a provider that still reports the card but drops the frame — a cancelled card leaves `result.accounts` entirely, so its `cardFrame` goes stale exactly like `balance` already does. `cardIssuer` is dropped when it reads `companyIssued` with no frame: Cal sets that in an unconditional `else`, making it a default rather than an observation.
- Isracard's `balanceDate` comes from a year-less `לחיוב ב-DD/MM` label, so moment stamps it with the current year and a December scrape of a January charge date lands ~11 months back. `scraped-balance.util.ts` rolls it forward a year when it's more than 3 months stale — scoped to isracard alone, since amex's date carries a real year and is legitimately a few weeks old.
- After the balance block, sync sweeps `AccountsService.upgradeUnknownAccountTypes` over the connection's account numbers to type auto-created accounts from `ACCOUNT_TYPE_BY_COMPANY`. It sits **outside** the balance try/catch on purpose — a provider whose balance we can't interpret still tells us whether its accounts are cards or bank accounts — and has its own try/catch so it can never fail an otherwise-good job. A provider mapped to `null` (Beyhad Bishvilha, a prepaid benefits card that is neither) is skipped rather than guessed at.
- Leumi (6.9.0+) returns savings/deposit accounts with `txns: []`. Transaction import never creates accounts for these, so `AccountBalanceService` creates the `Account` row itself — that's the only reason they're visible.
- `israeli-bank-scrapers` is installed from the shai-raz fork, pinned to a commit (`apps/api/package.json`): it sends Cal's data API calls from inside the browser (upstream sends them from Node, bypassing a browser proxy). Switch back to the npm release once upstream ships in-browser Cal API calls.
- With either browser, setting `CAL_PROXY_URL` runs each `visaCal` scrape in its own proxied browser context (Akamai rejects datacenter IPs; this is an Israeli proxy). IBS doesn't close a passed-in context, so `scrapeConnection` closes it in a `finally` after debug capture. If the proxied attempt fails (throws or `success: false`) for anything but a credential error (`INVALID_PASSWORD`, `CHANGE_PASSWORD`, `ACCOUNT_BLOCKED`, never retried, to avoid lockouts), it is retried once directly on the shared browser; look for the `retrying directly` warning in logs. Other providers are unaffected.
- **Scraped dates.** IBS's `BaseScraper.initialize()` sets `moment.tz.setDefault('Asia/Jerusalem')` globally, so every provider returns day D as Israel midnight in UTC (`D-1T21:00Z`), and this default leaks to any `moment()` call in the API process after the first scrape. `scrapeConnection` reads each date back in the provider's zone from `SOURCE_TIMEZONE_BY_COMPANY` (`@badger/shared-data`, all `IBS_DATE_TIMEZONE`, guarded by `ibs-date-timezone.spec.ts`) and stores UTC midnight of that day (`scraped-date.util.ts`). Never pass `new Date(txn.date)` straight to a `@db.Date` column. A provider from another library must declare its own zone deliberately.
