# transactions

Core ledger entries. Also owns FX conversion and the bank/sheet import pipeline (no controller of its own for the latter).

- Three `type`s: `income`, `expense`, `transfer`. `hidden` and `transferDirection` (`in`/`out`) are independent flags, not derived from `type` — a transaction can be an expense that's also hidden, etc. Transfers are excluded from income/expense totals wherever spend is aggregated (reports, budgets). Hidden expenses are excluded from those spend totals too (budgets, reports, MCP budget/spending tools), the same as the transactions summary, and the detail endpoint's `applicableBudgets` is empty for them.
- `mark-card-payoff` and the `card-payoff-patterns` module retag transactions as hidden transfers by exact description match — see `card-payoff-patterns/AGENTS.md`.
- `fx-conversion.service.ts`: `getRate()` is a read-only lookup (cache → provider fetch → throws if unresolvable); budgets and reports each decide differently how to handle a missing rate (see `budgets/AGENTS.md`). Provider is `freecurrencyapi.com`, gated by `FREE_CURRENCY_API_KEY`.
- `transaction-import.service.ts` is the shared landing zone for rows coming from `bank-sync` (scraper) and `google-sheets` (spreadsheet sync) — both call into it rather than writing `Transaction` rows directly. Look here first when import behavior (dedup, category resolution, currency handling) seems wrong regardless of which source triggered it.
- `transaction-import.service.ts` self-heals on re-sync. When a candidate carries `legacyTransactionDate`/`legacyPostedDate` (only bank-sync sets them, see `bank-sync/AGENTS.md` scraped dates), an existing row with the same externalId and account whose stored date equals that legacy value exactly is rewritten to the corrected date. Any other stored value (user edits) is untouched. It is best-effort and logged as a count of rows with corrected dates.
- `notes` (<=1000) and `additionalDescription` (<=150) limits are DTO-only (constants in `@badger/shared-data`); bank/sheet imports write to Prisma directly and stay uncapped, so the web edit form PATCHes (and validates) only changed fields.
- Synced rows (`externalId` set, by bank-sync or sheet import; app-created rows have none): `update()` rejects changes to amount, currencyId, transactionDate, postedDate, accountId, description, externalId and originalCategory (null counts), plus type/direction changes against the bank direction, via `synced-edit-lock.ts`. Internal `updateMany` callers (card payoff, mapping rules, category delete, importer) bypass it on purpose. `counterpartAccountId`/`counterpartAmount` are not locked fields, so they are allowed on synced rows.
- Linked transfers: a transfer may name one of the user's cash accounts as counterpart; the server keeps exactly one mirror row there (`counterpartOfId` -> source, opposite direction, wallet currency, same date/description/hidden, no category). `reconcileCounterpart` (`transfer-counterpart.ts`) is the single path that creates/moves/updates/removes the mirror, inside the source write's DB transaction. Deleting the source soft-deletes it and hard-deletes the mirror. The mirror is read-only except `notes` (`assertMirrorEditAllowed`; delete is refused) - a rule separate from the synced lock. Bulk writers must skip linked rows: card-payoff re-hide skips pairs, mapping-rule apply skips mirrors, and the importer date heal also moves the mirror's date. An existing mirror keeps its amount unless `counterpartAmount` is sent, so clients must send it whenever they change the source amount or currency; a `counterpartAmount` without a transfer + counterpart is rejected (create and update).
- `getSummary` backs linked transfer legs (source and mirror) out of `transferred` when there is no `accountId` filter (a second `groupBy` on the relation), so cross-currency pairs can't distort it; with an account filter they count as money leaving/entering it.
- Attachments are soft-deleted (`deletedAt`) and always filtered in `transactionInclude`.

- When adding filters to the reports/transactions UI or API, consider exposing them in the corresponding MCP tool (apps/api/src/mcp/tools) too.
